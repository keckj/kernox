# Core ↔ backends contract

Contract v0 and its amendments v0.1 to v0.10, all in force in kernox 1.0.
Code: [`kernox/plan.py`](../kernox/plan.py),
[`kernox/backends/base.py`](../kernox/backends/base.py).
Any change goes through this document; a backend does not change the
contract on its own side.

## Layering

| Layer | Owner | Content |
| --- | --- | --- |
| Frontend | core (`kernox/expr.py`…) | `Vi`, `Vj`, `Param`, operators, Python constants, `where`, reductions, `compile` |
| Plan | core (`plan.py`, `_plan_key.py`) | immutable, normalized `Plan` (reduction over `j`) |
| Runtime | core (`runtime.py`) | tensor validation, output allocation, backend selection, explicit errors |
| Pair function | core (`codegen/pair.py`) | scalar function generated by symox per dialect `cuda`, `hip`, `sycl` |
| Oracle | core (`oracle.py`) | blockwise Torch reference + small FP64 oracle |
| Reduction kernel | backends (`backends/{cuda,hip,sycl}/`) | tiling, accumulators, launch, cache, interop |

## Generated pair function

`kernox.codegen.pair.pair_function(plan, dialect) -> PairSource` produces an
inline device function, independent of the kernel strategy:

```c++
// dialect cuda/hip: __device__ __forceinline__ ; sycl: inline
struct kp_out { T o0; ...; T o{D-1}; };          // bool for COUNT
kp_out kp_pair(const T* __restrict__ xi_0, ...,   // one pointer per i arg: dim values
               const T* __restrict__ yj_0, ...,   // one pointer per j arg
               const T* __restrict__ p_0, ...);   // one pointer per param
```

Arguments are in the order of `plan.args`. The pointers designate the `dim`
contiguous components of the current row (registers, shared/local or global
memory depending on the backend). The generator relies on the symox printers
(`cudacode`, `_syclcode`), applies a region-based CSE in the presence of
`Piecewise`/`where` (below), never enables fast-math and
inserts no FP64 → FP32 conversion. Constants are emitted in the
plan's dtype (`double` literals or `f` suffix), conversions documented.
`PairSource` exposes: `source`, `name`, `out_type`, `arg_layout`.

Region-based CSE (`pair._region_cse`, generator `kernox-pair-v2`). A
common subexpression is hoisted (temporary evaluated unconditionally) if it
is already evaluated outside any branch (condition of the outer `where`,
unconditional part, another hoisted temporary) or if it appears in at least
two distinct regions (branches of different `where`s or of the same `where`);
otherwise it stays in its branch. Validity: the pair function is pure (no
memory written, no external call), and the targeted GPUs have no floating-point
trap: evaluating a subexpression outside its domain yields NaN/±inf without
interrupting the kernel, and this value is only read by the branches that
consume it; the ternary keeps the value of the active branch, that of a
non-hoisted evaluation (up to the choice of FMA contraction). Cost: at most one
speculative evaluation per shared temporary when none of its branches
is active. Exceptions: undefined functions other than the
`kp_pow*` helpers (user functions, unknown cost or side effects) are never
hoisted. The symox printers (C, Python) keep their own policy (no
CSE with `Piecewise`): region-based CSE is done by Kernox before
printing. Tests: `tests/test_pair_codegen.py` (structure) and
`tests/conformance/test_where_cse.py` (NaN, ±inf, 1/0 in the inactive
branch, against the FP64 reference, on each backend).

General extensions useful to other projects (standalone CUDA device
function, output struct) are to be proposed to symox; until they are
published there, they live in `codegen/pair.py` and are marked as such.

## Reduction semantics (reduction over j, for each i)

Inputs: `i` arg (M, d), `j` arg (N, d), param (d,), dtype `plan.dtype`,
contiguous (non-contiguous strides explicitly rejected by the runtime), same
device. Output shapes: `plan.output_shapes`.

| Reduction | Identity (N = 0) | Ties | NaN |
| --- | --- | --- | --- |
| SUM | 0 | n/a | propagated (IEEE arithmetic) |
| COUNT | 0 (int64) | n/a | a comparison with NaN is false |
| MIN / MAX | +inf / −inf | n/a | NaN candidate **ignored** |
| ARGMIN / ARGMAX | −1 | smallest index j | NaN candidate ignored; if no candidate: −1 |
| KMIN / ARGKMIN | +inf / −1 as padding | lexicographic order (value, j) | NaN candidate ignored |

- Order of the K outputs: increasing values, ties by increasing index.
- `K = 0`: outputs of shape (M, 0), no launch. `K > N`: padding with
  (+inf, −1). `K < 0` or non-integer: error before any launch.
- KMIN/ARGKMIN: scalar formula (`out_dim == 1`) only in v0, otherwise
  `UnsupportedError`.
- `±inf` is a valid value (not an absent candidate). A candidate equal to
  +inf can therefore be returned with an index ≥ 0.
- `M = 0`: empty outputs, no native launch.
- Indices: int64, never stored as floating point; N must fit in int64.
- COUNT: int64 accumulator, no overflow possible for N < 2^63.
- SUM: `acc_dtype` accumulator (default = `dtype`). The summation order
  is not specified; test tolerance relative to the L1 norm of the terms.

## Execution rules

- The kernel runs on the current Torch stream (`torch.cuda.current_stream`
  for CUDA and ROCm, `torch.xpu.current_stream` for XPU) of the tensors'
  device. No host synchronization in `launch`.
- No materialized M×N matrix. Bounded temporaries, allocated by Torch,
  size published in `CompileInfo.temp_bytes_per_launch`.
- No unsupported operation is replaced by a CPU or Torch computation
  advertised as GPU: `UnsupportedError`.
- Atomic disk cache (temporary file + rename), key = `plan.key()` +
  generator version + compiler + options + architecture. Concurrent
  compilation protected by a file lock.
- FP64 explicitly rejected on a device that does not support it.

## Support states

Each cell of the support matrix (backend × reduction × dtype × GPU)
takes one state among: planned, implemented, compiled, tested (correctness
corpus on the real GPU), qualified (tested + large-case benchmarks published).

## Amendment v0.1 (backward-compatible additions)

No v0 field or behavior is removed.

- **Building a plan**: `kernox.builder.make_plan(outputs, kind, dtype,
  args=..., k=..., acc_dtype=...)` and `make_arg(name, role, dim)` (validation,
  conversion of constants). The frontend (`ReductionExpr.to_plan`) uses it and
  orders the arguments i, then j, then param, each by name.
- **v0 restriction**: at least one i argument and one j argument (otherwise M or N
  cannot be inferred) → `UnsupportedError`. `acc_dtype ≠ dtype` reserved for SUM.
- **`PairSource`**: added fields `dialect`, `scalar_type` (T), `out_fields`
  (`o0`…), `out_ctypes` (`float`/`double`/`bool`), `generator_version`,
  property `sha256`. `arg_layout` is a tuple of `ArgLayout(param, arg, role,
  dim)`; C names `xi_<n>`, `yj_<n>`, `p_<n>` (rank among the args of the same role).
  `pair_function(plan, dialect, name=..., out_type=...)` allows several plans
  in the same compilation unit.
- **Source content**: defines, under the `#ifndef KP_PAIR_HELPERS` guard, the
  functions `kp_pow2/3/4` (float and double overloads); in cuda/hip, defines
  `INFINITY`/`NAN` if they are absent. The backend must not redefine these names.
  SYCL: `<sycl/sycl.hpp>` must be included before the source; HIP: HIP runtime
  (included automatically by hipcc/hiprtc); CUDA/NVRTC: no header required.
- **Backend registry**: a native backend is a module
  `kernox.backends.<name>` exposing `get_backend() -> Backend`, or an object
  registered by `kernox.runtime.register_backend(name, factory)`. Absent →
  `BackendUnavailableError`, without fallback.
- **`CompileInfo.backend`** can be `"oracle"` (blockwise Torch reference,
  never chosen by `auto`).
- **Runtime**: `M = 0` and `K = 0` are handled by the core without calling
  `launch`; `N = 0` remains the responsibility of `launch` (filling with identities),
  in accordance with v0.

## Amendment v0.2: optional autotuning with effort levels

Fast autotuning, inspired by FFTW's planning levels,
**disabled by default**.

API: `compile(expr, dtype=..., backend=..., tuning="estimate")`.

| `tuning` | Behavior |
| --- | --- |
| `"estimate"` (default) | heuristic variant `default_variant`, no measurement, no wisdom read; deterministic |
| `"wisdom_only"` | variant from the wisdom if it exists for the key, otherwise `estimate`; no measurement |
| `"measure"` | wisdom if present; otherwise measures at most 4 candidates `variants(..., "measure")`, keeps the fastest, records it |
| `"patient"` | same with at most 32 candidates `variants(..., "patient")` |

Backend: `default_variant`, `variants` and `compile(plan, device, variant)`
(see `backends/base.py`, classes `Sizes` and `Variant`). `CompileInfo` carries
the effective variant (`info.variant`).

Wisdom key: `plan.key()`, backend, device identifier (name, arch, UUID
if available), driver/compiler/generator versions, and **size class**
in half-octaves `(ceil(2 log2 M), ceil(2 log2 N), ceil(2 log2 nb),
ceil(2 log2 1/ρ))` (and K via the plan; v2: the octave class could
reuse a worse decision; v3: `nb`
batch elements and ranges density `ρ`, 0 and 0 without batch or ranges;
v2 entries are migrated to `(M, N, 0, 0)` on read and on import). Exact sizes trigger neither recompilation nor new
measurement within a class. An entry carries its effort level and
is only reused by a lower or equal level (`patient` does not reuse
a `measure` decision).

Measurement:
- only on the first call of a size class without wisdom; the call
  is then **blocking** (synchronization), which is documented;
- on the real inputs of the call (read-only), outputs in
  temporary tensors; compilation excluded from timing but published;
- GPU events on the current stream, 1 warm-up then median of
  several launches, time budget bounded and published per level;
- if the measured dispersion is high (shared GPU, unstable frequency), the
  result **is not persisted** and the decision is marked unstable:
  a wisdom measured on a busy GPU must not impose itself afterwards;
- the result of the call is that of the selected variant, recomputed or
  kept, never that of a discarded variant.

Wisdom: one JSON file per device under the Kernox cache directory, written
atomically and protected by a lock; `export_wisdom()`, `import_wisdom()`,
`forget_wisdom()`. An invalid entry or one from a different version is ignored.

Semantics: changing variant changes neither the semantics (ties,
NaN, indices) nor the dtypes. For floating-point SUM, the summation order may
differ from one variant to another; results stay within tolerance.
With `tuning="estimate"`, the result is reproducible for a given device.

Benchmarks: each result publishes the tuning level and the variant
used; the comparison with PyKeOps distinguishes `estimate` and the measured
levels, the tuning time being published separately.

Bounds: `measure` ≤ 4 candidates, `patient` ≤ 32 candidates. Correctness tests may run on shared GPUs;
benchmarks and persisted tuning measurements, only on a free GPU.

### Note on the tuner implementation (v0.2)

Optional, backward-compatible additions on the backend side: `device_identity(device) ->
dict` (stable identity for the wisdom: name, arch, UUID,
driver/compiler versions); failing that, the core uses the `CompileInfo` of the default
variant. A backend whose `compile` does not accept `variant` is treated as
having no variants (explicit fallback to `estimate`). Candidate bounds
enforced by the core (truncation + log). Details: `docs/api.md`.

## Amendment v0.3: FMA contraction

Observation: CUDA (NVRTC, `--fmad=true` by default) and SYCL (`-fp-model=precise`)
contracted `a*b + c` into an FMA, HIP forbade it (`-ffp-contract=off`).

Decision, uniform for all backends:

- **By default, FMA contraction *within an expression* is
  allowed** (`Plan.fp_contract = True`), like nvcc/NVRTC and PyKeOps.
  An FMA rounds once instead of twice: this is neither fast-math, nor
  reassociation, nor a loss of precision. Results may differ in the
  last bit from one backend to another; test tolerances account for it.
- `fp_contract=False` (option of `compile`) enforces no contraction
  on all backends (`--fmad=false`, `-ffp-contract=off`,
  `-fp-model=strict` or `-ffp-contract=off` depending on the compiler), for
  bit-for-bit reproducibility across backends. The option is part of the
  cache key.
- Still forbidden by default (opt-in fast-math: amendment v0.10): fast-math, reassociation, approximations
  (`__expf`, unrequested `rsqrt`…), FTZ/DAZ, TF32, FP64 → FP32 demotion.
- Benchmarks publish the value of `fp_contract`.

## Amendment v0.4: gradients of SUMs

No new requirement for backends: gradients are ordinary SUM plans
built by the core (`kernox.autograd.gradient_plans`) and
compiled by the same backend as the forward pass.

For `out[i, e] = Σ_j F_e(x_i, y_j, p)` and an upstream gradient `G` (M, E), an
additional input named `kp_grad` (numeric suffix if the name is taken):

- i-side plan (roles unchanged, `G` with role i): outputs
  `Σ_e G_e ∂F_e/∂x[c]` for each component of the requested i args, then
  `Σ_e G_e ∂F_e/∂p[c]` for the requested parameters (summed over i by Torch);
- j-side plan (i/j roles swapped, `G` with role j): `Σ_e G_e ∂F_e/∂y[c]`;
- same `dtype`, `acc_dtype` and `fp_contract` as the forward plan;
  `meta = {gradient_of: key of the forward plan, gradient_side}` (outside the key).

Derivatives: `symox.diff` then `Heaviside(z)` → 1 / 0 / 1/2 (z > 0, z < 0,
z = 0), `DiracDelta` → 0, unevaluated `Derivative` → `UnsupportedError`. The
`Piecewise` is differentiated branch by branch (gradient of the active branch);
region-based CSE applies to gradient plans as to the others. The
reductions other than SUM are not differentiable (explicit error at
`backward` for floating-point outputs; integer outputs without gradient).

Tests: `tests/test_autograd.py` (oracle: `gradcheck`, `gradgradcheck`, dense
Torch, rules, rejections) and `tests/conformance/test_autograd.py` (each GPU
backend: dense Torch in FP32/FP64, FP64 `gradcheck` and `gradgradcheck`).


## Amendment v0.5: LOGSUMEXP and SUMSOFTMAXWEIGHT

Two new `ReductionKind`s, equivalent to PyKeOps' `LogSumExp` and
`SumSoftMaxWeight`. A backend that does not implement them yet
answers `Support(False, ...)`; the runtime then raises `UnsupportedError`.

| Reduction | Plan `outputs` | Output | Definition |
| --- | --- | --- | --- |
| `LOGSUMEXP = "logsumexp"` | `(f_1, …, f_D)` | `value` (M, D), `acc_dtype` | `out[i, d] = log Σ_j exp f_d(i, j)`, each component independent |
| `SUMSOFTMAXWEIGHT = "sumsoftmaxweight"` | `(f, g_1, …, g_E)`: scalar `f`, then `E ≥ 1` components | `value` (M, E), `acc_dtype` | `out[i, e] = Σ_j exp f(i,j) · g_e(i,j) / Σ_j exp f(i,j)` |

`Plan.meta` plays no role; for SUMSOFTMAXWEIGHT, the plan's `out_dim` is
`1 + E` and `output_shapes` returns (M, E).

**Mandated algorithm (stability)**: shift by the running maximum, in
a single pass over j (no second pass nor M×N matrix). State per
row and per component: `(m, s)` (and `(m, s, t_1..t_E)` for SSMW), in
`acc_dtype`. Insertion of a term `v` (and `w_e`) and merging of two states
(tiles, j-splitting):

```
m' = max(m1, m2)
s  = s1·exp(m1 − m') + s2·exp(m2 − m')       (t_e likewise)
```

with the convention `exp(−inf − (−inf)) = 0`: an empty state (`m = −inf`,
`s = 0`) is the identity for merging, without NaN. Result: `m + log(s)` for
LOGSUMEXP, `t_e / s` for SUMSOFTMAXWEIGHT.

**Special values** (difference with MIN/MAX: nothing is ignored):

- N = 0, or all `f = −inf`: LOGSUMEXP → `−inf`; SUMSOFTMAXWEIGHT → NaN
  (0/0, like PyKeOps).
- An `f = +inf`: LOGSUMEXP → `+inf`; SUMSOFTMAXWEIGHT → NaN (inf/inf).
- A NaN `f` or a NaN `g_e` with nonzero weight: NaN (propagated, like SUM).
- A NaN `g_e` on a term of exactly zero weight (`f = −inf`) is ignored:
  the term does not exist.
- Exact `exp` and `log` from the backend's libm (no `__expf`, no
  fast-math), FMA contraction according to `fp_contract`.

**Test tolerance**: against the FP64 reference (`torch.logsumexp`,
`torch.softmax` in blockwise dense FP64), relative error bounded as a function
of `log N`, like SUM; mandatory adversarial cases: large `f` (1e4, no
overflow thanks to the shift), very negative `f` (−1e4), mix of `±inf`,
N = 0, N = 1, a single dominant row, j-splitting with empty slices.

**Gradients** (core, after v0.4): `∂ LSE/∂θ = Σ_j softmax_ij ∂f/∂θ`, i.e.
a SUMSOFTMAXWEIGHT reduction generated by `symox.diff`. The gradient of
SUMSOFTMAXWEIGHT combines two SUMSOFTMAXWEIGHTs. Both are planned for
the "gradients" step; until then, `backward` raises `UnsupportedError`.

## Amendment v0.6: batch dimensions and block-sparse ranges

Backward-compatible: a plan without batch or ranges is unchanged (same key, same
kernel). Functional reference: PyKeOps (batch dimensions of
`LazyTensor`, `ranges` argument, `pykeops.torch.cluster`); no line of
KeOps code reused (any reuse goes through `THIRD_PARTY.md`).

**Decisions**: (a) ranges passed via
`run.with_ranges(r)(**inputs)`, no reserved name; (b) no Python loop
`batch="loop"`, even on request: a backend without batch answers
`Support(False)`, the loop is left to the user; (c) implementation
order below (batch then ranges; oracle and runtime first, backends
`Support(False)`, then backends one by one).

### 1. Batch dimensions: implemented (step 1: runtime, oracle, autograd)

Semantics:

- `i` arg `(*Bi, M, d)`, `j` arg `(*Bj, N, d)`, param `(*Bp, d)` or `(d,)`;
  **same batch rank** `r` for all i and j inputs (no implicit
  insertion); Torch broadcasting (size 1 or equal): `B = broadcast(Bi, Bj, Bp)`.
  Outputs `(*B, M, out)` (indices `(*B, M, K)`).
- Each batch element is an independent v0 reduction (identities, NaN,
  ties, K padding, `sum_scheme`); **local indices** `0 ≤ j < N`.
  `over="i"`: normalization unchanged.
- `prod(B) = 0`, `M = 0` or `K = 0`: empty outputs, no launch (the
  backend must nevertheless accept the batched plan); `N = 0`: identities via `launch`.
- Validation: common rank, broadcasting possible, exact dtype, same device;
  **last two dimensions contiguous** (last one with stride 1 if `d > 1`,
  second-to-last with stride `d` if `L > 1`); batch dimensions with arbitrary
  strides, 0 included (`expand`), without copy.

Form in the Plan: `Plan.batch_rank: int = 0`, in the key only if it
is nonzero; batch sizes outside the key. `output_shapes(plan, m, batch=())`
prepends `batch`. The frontend compiles a `batch_rank = 0` plan; the runtime
derives from it (and caches) the `batch_rank = r` variant on the first batched call.
A `Plan` provided with `batch_rank = r` requires inputs of rank `r`.

Runtime ↔ backend contract:

- The backend declares the attribute `batch = True` (absent = False: the runtime
  rejects any batched plan with `UnsupportedError`, in addition to `supports`).
- `launch(inputs, outputs, *, batch=BatchLayout)`; `BatchLayout(shape, nb,
  offsets, host_offsets)`: per argument, an int64 table `(nb,)` of offsets **in
  elements** relative to `data_ptr` (broadcasting = repeated offsets, param without
  batch = zeros), on the device (`offsets`) and on the host (`host_offsets`,
  for references; a native backend does not read them in `launch`).
  Tables computed by Torch and cached by (device, B, shapes,
  strides): one host → device copy on the first call of a configuration,
  none afterwards.
- Inputs passed as is (original batch shapes and strides);
  contiguous outputs `(nb, M, …)`, then viewed as `(*B, M, …)`.
- The kernel reads the offset of its element once per block (batch index as a
  grid dimension or fused with the i-block axis); the j-splitting
  variants remain valid (temporaries `(nb, S, M, …)`).
- `Sizes.nb` (default 1). Measured autotuning of batched plans: wisdom v3,
  `⌈2 log2 nb⌉` in the size class; candidates are launched with the
  same `BatchLayout` as the call.

Gradients: per element, as in v0.4; gradients of broadcast inputs
reduced by `sum_to_size` (Torch, outside the kernel); batched params summed over M
within the element. The gradient of a batched SUM keeps `sum_scheme`.

Tests: `tests/test_batch.py` (CPU); `tests/conformance/test_batch.py`
(oracle executed; backends explicitly skipped as long as they answer
`Support(False)`): broadcasting `(B1,1)×(1,B2)`, params `(d,)`/`(*B,d)`,
0 and non-standard strides, prime `nb`, `prod(B) = 0`, bit-for-bit equality
with a loop of v0 calls except SUM, local indices, `over="i"`, FP64 gradcheck
and gradgradcheck with broadcasting.

### 2. Block-sparse ranges: implemented (step 1: runtime, oracle, autograd)

`kp.Ranges` carries the six int32/int64 tensors of PyKeOps, on the device of the
inputs: `ranges_i (Ci, 2)` row blocks `[a, b)`, `slices_i (Ci,)` cumulative
ends into `redranges_j (Ri, 2)` intervals of j to reduce, and the transposed
triplet `ranges_j`, `slices_j`, `redranges_i`.

- For i in block c: reduction over `J(i) = ∪ redranges_j[slices_i[c−1] :
  slices_i[c]]`. A row covered by no block receives the **identity**.
- Disjoint i blocks, disjoint intervals within a block; checked if
  `validate_ranges=True` (O(C+R) on the device), otherwise overlap = undefined.
- Ties: smallest j of `J(i)`, whatever the order of the intervals.
- `over="i"`: the runtime swaps the triplets. The j-side gradient requires the
  transposed triplet (explicit rejection otherwise). Ranges + batch: rejected in v0.6.
- Call: `run.with_ranges(r, validate=False)(**inputs)` (decision a),
  returns a `RangedReduction`. Torch helpers:
  `kp.ranges_from_labels(labels_i, labels_j, keep)` (sorted labels, two
  triplets), `kp.Ranges.dense(M, N, device)`. `validate=True` checks the
  values on the device (one host synchronization per call); shapes,
  dtypes (int32/int64) and devices are always checked.
- Plan: `Plan.ranges: bool = False`, in the key only if it is true;
  tensors outside the key. The runtime derives the `ranges=True` plan and normalizes the
  forward-pass triplet (plan orientation) into a device work
  list: tiles `(i0, i1, k0, k1)` int64 of height ≤ `tile_m`, where `tile_m`
  is published by the compiled object (`ranges_tile_m`); Torch computation (its size
  requires a host synchronization), cached by identity, version and
  shape of the ranges tensors.
- The backend declares `ranges = True` (absent = rejection by the runtime, in addition
  to `supports`); `launch(inputs, outputs, *, ranges=RangesLayout(work,
  redranges, tile_m, host_work, host_redranges))`; the tile reduces its
  rows over `∪ redranges[k0:k1]`; uncovered rows receive the
  identity (responsibility of `launch`). Measured autotuning: wisdom v3,
  `⌈2 log2(1/ρ)⌉` in the size class (ρ: covered pairs / M·N,
  computed outside `estimate` only, host synchronization); each candidate
  is launched with the work list of its own `ranges_tile_m`.
- Gradients: i side (i args and params) with the forward triplet; j side with
  the transposed triplet (explicit `UnsupportedError` if missing); order 2
  by the same mechanism; `sum_scheme` preserved.
- Tests: `Ranges.dense` ≡ without ranges (bitwise except SUM); label
  masks (densities 1, 0.5, 0.05, 0), empty blocks, uncovered rows,
  out-of-order intervals, blocks taller than `tile_m`, overlaps
  rejected, K > |J(i)|, gradients with and without transposed triplet, masked
  FP64 oracle, comparison with PyKeOps `ranges` on NVIDIA.

### Implementation order (decision c)

1. Oracle and runtime, `Support(False)` on cuda/hip/sycl (one commit per
   backend): batch and ranges done (tests `tests/test_batch.py`,
   `tests/test_ranges.py`, conformance `test_batch.py`, `test_ranges.py`).
2. Backends one by one (offset per block, then work list), promotion
   in `docs/support-matrix.md` upon proof.
3. Wisdom v3 and autotuning of batched / ranged plans: done on the runtime side
   (`tests/test_tuning.py`, dummy backend); real measurement as soon as a native
   backend declares `batch`/`ranges`.

## Amendment v0.7: summation schemes

Equivalent of PyKeOps' `sum_scheme` option (`direct_sum`, `block_sum`,
`kahan_scheme`). Added field: `Plan.sum_scheme: Literal["direct", "block",
"kahan"] = "direct"`, in the plan key; option `compile(..., sum_scheme=)`.

Applies to floating-point accumulations: SUM, and the sums `s`, `t_e` of
LOGSUMEXP / SUMSOFTMAXWEIGHT. Ignored (without error) for COUNT, MIN/MAX, ARG*,
KMIN*, which do not accumulate floating-point values.

| Scheme | Definition (per row i, per component) |
| --- | --- |
| `direct` | current behavior: one `acc_dtype` accumulator per thread, partials of tiles/slices added together. The order is not specified. |
| `block` | each j tile (size `T` ≤ the backend's tile size, published in `CompileInfo.options`) is summed into a fresh accumulator, then added to the total. Error bound ≈ `(N/T + T)·u·Σ|term|` instead of `N·u·Σ|term|`. |
| `kahan` | Kahan–Babuška (Neumaier) compensated summation in `acc_dtype`: state `(s, c)`, insertion `t = s + x ; c += (|s| ≥ |x|) ? (s − t) + x : (x − t) + s ; s = t`. Merging of two states (tiles, j-splitting): `TwoSum(s1, s2)` + `c1 + c2`. Result `s + c`. Error bound ≈ `2u·Σ|term| + O(N u²)`, independent of N to first order. |

**Rules:**

- No compiler option must be able to destroy the compensation: no
  fast-math (already forbidden), no reassociation. The compensation only uses
  additions/subtractions, so `fp_contract` does not affect it; the
  backend checks this with a test (Higham data below) with
  `fp_contract` set to `True` and to `False`.
- `kahan`: if the sum `s` is not finite (±inf, NaN), the result is `s`
  (the compensation `c = inf − inf` would be NaN).
- For LOGSUMEXP / SSMW, the rescaling factor `exp(m_old − m_new)`
  applies to `s` **and** to `c` (and to `t_e`, `c_e`).
- Cost: `kahan` roughly doubles the accumulation state; a backend publishes the
  effective variant and `temp_bytes_per_launch` accordingly.
- A backend that does not implement a scheme answers `Support(False, ...)` for
  that scheme (`UnsupportedError`), never a silent fallback to `direct`.

**Tests (conformance):**

- Ill-conditioned data: `±1e8` terms that cancel out plus small
  terms, in FP32 (reference `math.fsum` in FP64), N from 10³ to 10⁶.
- Requirements: FP32 `kahan` ≤ `4u·Σ|term|` (+ documented margin) whatever N;
  `block` ≤ `(N/T + T + 2)·u·Σ|term|`; `direct` ≤ current bound. And
  above all, on this data: error(`kahan`) < error(`direct`) by at least one
  order of magnitude for N ≥ 10⁵ in FP32.
- Forced j-splitting (multiple slices, empty slices), various tile
  counts K, FP64 `acc_dtype` with FP32 compatible with all three schemes.
- Benchmarks: cost of `block` and `kahan` versus `direct` on the reference SUM,
  LSE and SSMW cases, and versus PyKeOps with the same `sum_scheme`.

## Amendment v0.8: MIN_ARGMIN, MAX_ARGMAX, LOGSUMEXPWEIGHT

Three PyKeOps-parity `ReductionKind`s (`min_argmin`, `max_argmax`,
`logsumexp(weight=)`). A backend that does not implement them yet answers
`Support(False, ...)` (cuda, hip and sycl do so in this batch); the oracle
implements them.

| Reduction | Plan `outputs` | Outputs | Definition |
| --- | --- | --- | --- |
| `MIN_ARGMIN = "min_argmin"` | `(f_1, …, f_D)` | `value` (M, D) `dtype`, `index` (M, D) int64 | MIN and ARGMIN **from the same pass**: `value[i,d] = f_d(i, index[i,d])` |
| `MAX_ARGMAX = "max_argmax"` | same | same | MAX and ARGMAX |
| `LOGSUMEXPWEIGHT = "logsumexpweight"` | `(f, g_1, …, g_E)`: scalar `f`, `E ≥ 1` | `value` (M, E), `acc_dtype` | `out[i,e] = log Σ_j exp f(i,j) · g_e(i,j)` |

- MIN_ARGMIN / MAX_ARGMAX: ties, NaN and identity exactly those of MIN
  and ARGMIN (smallest index j; NaN candidate ignored; no candidate:
  `(+inf, −1)` / `(−inf, −1)`). The runtime returns the tuple `(values, indices)`,
  like KMIN_ARGKMIN. As for ARGMIN, the indices are not
  differentiable; gradients of the values belong to the gradients step.
- LOGSUMEXPWEIGHT: same state and same algorithm as SUMSOFTMAXWEIGHT
  (`(m, s, t_e)` shifted by the running maximum, `s` unused in the result),
  result `m + log(t_e)` **without special cases**:
  - N = 0 or all `f = −inf`: `t_e = 0` → `−inf`;
  - an `f = +inf`: `t_e = Σ_{f=+inf} g_e` → `+inf` if `t_e > 0`, NaN otherwise;
  - `t_e < 0` (negative weights): NaN, like `log`; NaN `f`: NaN;
  - NaN `g_e` on a term of exactly zero weight (`f = −inf`): ignored,
    like SUMSOFTMAXWEIGHT.
- `sum_scheme` (amendment v0.7) applies to `t_e` as for SUMSOFTMAXWEIGHT;
  `acc_dtype` distinct from `dtype` allowed.
- Plan key: the name of the `ReductionKind` is already part of it; no existing key
  changes.
- Tests: `tests/test_reductions_v08.py` (Torch oracle against the independent
  NumPy reference `reduce_numpy`, special values, batch, ranges);
  conformance `tests/conformance/test_reductions_v08.py`, skipped on a
  backend that answers `Support(False)`.

## Amendment v0.9: FP16

PyKeOps parity `dtype="float16"`. `DType` gains `"float16"`.

- **Computation**: inputs and formula in binary16, each operation rounded in
  FP16 (semantics of the Torch oracle; a native backend may compute in
  `half`/`half2`, FMA contraction remains governed by `fp_contract`).
  Python constants and parameters: same policy as in FP32 (rounded once
  to FP16, `ConstantConversionError` beyond 65504 or for a
  nonzero value rounded to 0; FP16 subnormals are representable).
- **Accumulator**: default `acc_dtype` **`float32`** for SUM,
  LOGSUMEXP, SUMSOFTMAXWEIGHT and LOGSUMEXPWEIGHT (state `(m, s, t)` included),
  `float16` for the other reductions (no accumulator). Allowed `acc_dtype`:
  `float16` or `float32` (like PyKeOps; `float64` rejected).
  (a) The FP32 default is a **deliberate deviation**: PyKeOps uses
  `dtype_acc = dtype` (`"auto"` → `half2`).
- (b) **Outputs**: a `float16` plan returns `float16`, including SUM and the
  LOGSUMEXP family: **exception** to the "output in `acc_dtype`" rule
  (type parity with PyKeOps). Final conversion of the accumulator to FP16
  round-to-nearest, `±inf` beyond 65504 (`plan.accumulated_output_dtype`).
- (c) `acc_dtype="float16"` reproduces PyKeOps: accumulation in FP16 and
  `sum_scheme="block"` by default (PyKeOps' `block_sum`); an explicit
  `sum_scheme` is still honored.
- MIN/MAX/KMIN return FP16, ARG*/COUNT int64. `sum_scheme`
  (amendment v0.7) applies in `acc_dtype`.
- Gradients: same plans, in FP16 (accumulators of the gradient SUM plans
  in `acc_dtype`); gradients returned in the dtype of the inputs.
- **Backends**: `Support(False, "dtype ... float16 ...")` as long as they do not
  implement it (cuda, hip, sycl in this batch: rejection before any
  launch). Plan key: `dtype` is already part of it.
- Tests: `tests/test_fp16.py` (oracle: accumulator defaults, FP16
  computation proven by overflow, FP16 accumulator rounded at each addition,
  schemes, constants, parameters, gradients); conformance
  `tests/conformance/test_fp16.py` (explicit rejection or equality with the oracle).

## Amendment v0.10: opt-in fast-math: approximate exp and log

Observation (2080 Ti): on LOGSUMEXP at small dimension, the remaining gap
against GeomLoss comes from PyKeOps' approximate `exp` (`-use_fast_math`: 2
instructions, FMUL + MUFU.EX2, versus ~9 for IEEE `expf`). Example: Sinkhorn
D = 2, 10⁵ points, 26.5 ms versus 22.0 ms. In IEEE mode, Kernox is faster than
PyKeOps.

Decision:

- **`Plan.fast_math`** (`compile(..., fast_math=True)`, `to_plan`, `make_plan`)
  allows **approximate** `exp` and `log`.
  - Default: `False`. IEEE behavior is unchanged, bit for bit.
  - The flag is part of the plan key, and gradient plans inherit it.
- **Scope.**
  - Only `exp` and `log` are approximated: those of the formula, and those internal to
    the reductions (max-shift state of LOGSUMEXP, SUMSOFTMAXWEIGHT and LOGSUMEXPWEIGHT,
    final log).
  - Divisions, roots, trigonometric functions, FTZ/DAZ and reassociation
    remain IEEE, as without the option.
  - Edge cases do not change: exp(−inf) = 0, exp(+inf) = +inf, log(0) =
    −inf, log(x < 0) = NaN, and NaN propagates.
- **CUDA.**
  - FP32: `exp(x) = ex2.approx.f32(x·log₂e)` and
    `log(x) = lg2.approx.f32(x)·ln 2`, without `.ftz`, so subnormals are
    preserved. These are the instructions PyKeOps uses.
  - FP64: no approximate instruction exists, the computation stays IEEE (the generated
    source is identical). This is also the case for PyKeOps.
  - FP16: `UnsupportedError` for now.
- **HIP and SYCL** raise `UnsupportedError` as long as they do not implement
  the amendment. A backend must never silently ignore the flag.
- **The oracle stays IEEE**: it serves as the reference.
- **Conformance tolerances** (`tests/conformance/test_fast_math.py`, FP64
  reference, `u = 2⁻²⁴`):
  - Approximate `exp`: relative error ≤ 2⁻²¹ + |x|·u. The first term comes from
    the instruction; the second, from the rounding of x·log₂e amplified by 2^·.
  - Approximate `log`: absolute error ≤ 2⁻²¹.
  - Sums of N terms: + N·u.
  - Test threshold: `8·(2⁻²¹ + X·u) + 2·N·u`, with X = max |argument of exp|. It
    is relative for sums of positive terms, and absolute/(1 + |ref|) for
    LOGSUMEXP.
  - For a sum with cancellation: `|err| ≤ threshold·Σ|term| + 2·2⁻²¹·Σ|weight|`.
  - The test also checks that the fast-math outputs differ from the IEEE outputs,
    to make sure the approximation is actually active.
- **Benchmarks.** They publish the value of `fast_math`. The parity verdict remains
  measured against IEEE PyKeOps. The comparison with fast-math PyKeOps is done with
  `fast_math=True`.
